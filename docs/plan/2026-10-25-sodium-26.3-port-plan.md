# Plan: Sodium support for DirectExp on Minecraft 26.3

**Basis:** static reading of `DirectExp.zip` (MC 26.3, `renderpearl` API), `Direcium.zip` (written for MC 26.2 / Sodium 0.9.2) and `sodium-dev.zip` (Sodium dev tree, `MINECRAFT_VERSION = "26.3"`).
**Not verified by running anything.** Nothing here was compiled or launched. "Verified" means read in source.

---

## 1. Summary

1. **Direcium as it exists will not compile or load on 26.3.** Sodium's draw path was rewritten and Mojang's GPU types moved from `com.mojang.blaze3d.*` to `com.mojang.renderpearl.*`.
2. **The rewrite makes the bridge much smaller.** Sodium 26.3 sends per-region data with `pass.pushConstants(...)` itself and has a generic multi-draw path (`VK_MULTIDRAW`) that only needs `RenderPass.multiDrawIndexed(IntBuffer, ...)`. DirectExp already implements both. Direcium shrinks from about 7 classes plus 3 mixins to **one mixin** that makes Sodium choose `VK_MULTIDRAW` when DirectExp is the active backend.
3. **DirectExp needs no required code changes**, based on reading. Its `docs/plans` are stale in places (section 3), so do not plan from them.
4. **One real gap is not a rendering problem:** DirectExp puts its Graphics API option into vanilla's `VideoSettingsScreen`, and Sodium replaces that screen. Under Sodium the option becomes unreachable. Direcium should register it through Sodium's config API.
5. The main unknowns can only be settled by a Windows run: LWJGL Vulkan classes on the classpath, SPIR-V to HLSL for Sodium's shaders, OIT, and large-arena buffer limits (section 7).

## 2. What changed in Sodium 26.2 to 26.3 (breaks Direcium)

| Area | Direcium (26.2) assumes | Sodium 26.3 actually has | Consequence |
|---|---|---|---|
| Mojang package | `com.mojang.blaze3d.systems.{RenderPass, GpuDevice, RenderPassBackend}`, `com.mojang.blaze3d.pipeline.RenderPipeline` | `com.mojang.renderpearl.api.commands.RenderPass`, `...api.device.GpuDevice`, `...api.pipeline.RenderPipeline`, `...backend.api.RenderPassBackend` | Every Direcium import fails to compile. `RenderPassBackendAccessor` targets a class that no longer exists, so with `required: true` the game crashes at mixin load. |
| `DrawContext` API | `updateData(RenderRegion, CameraTransform)`, protected static `getCameraTranslation(...)` | `DrawContext` has only `create()`, `getPass()`, `setContext`, `rotate`, `delete`, `endDraw` | `DireciumDrawContext` has `@Override`s with nothing to override. |
| Per-region data | Bridge computes camera offset, time, region id and calls `setPushConstants` | `DefaultChunkRenderer.render` computes all three and calls **`pass.pushConstants(memory)`** (20 bytes: 3 floats, `int` time at 12, `uint` region id at 16) before each `batch.draw(...)` | The whole push-block / time / region-offset part of Direcium is redundant. |
| Pipelines | Push-constant block implied by shader | `.withPushConstantSize(20)`, `BindGroupLayout` with `u_SectionTimeInfo` as `TEXEL_BUFFER R32_SINT`, `u_LightTex` in a second group, OIT via `OitPipelineSet` | No change needed in the bridge, but these are the features DirectExp must handle (section 5). |
| Backend selection | `DrawContext.create()` and `MultiDrawBatch.newBatch` each `switch` on `DrawBackend.BACKEND` | Same, but enum is now `OPENGL, VK_MULTIDRAW, VK_INDIRECT`. `chooseBackend()` picks a Vulkan variant only if `sodium$getBackend() instanceof VulkanDevice`; otherwise `OPENGL` | DirectExp is not a `VulkanDevice`, so Sodium picks `OPENGL`. That selects `GLDrawBatch`, which calls the separate-array `multiDrawIndexed(PointerBuffer, IntBuffer, IntBuffer, int)` and DirectExp throws `UnsupportedOperationException` on it. This is the single seam to fix. |
| Batch layout | OpenGL batch shifts `elementOffset << 2` (bytes), Vulkan batch does not | Unchanged | Direcium's old note "elementOffset is in index units" still applies to the VK batch. |
| Sodium mixins on GL types | n/a | `GlFallbackAllocatorMixin`, `WindowMixin` (on `GlBackend`), `GlStateManagerMixin`, `GlSurfaceMixin` | Targets exist in the Minecraft jar but are never instantiated on DirectX. `GlSurfaceMixin` and `SodiumConfigBuilder` are already guarded by `backendName().contains("OpenGL")`; DirectExp reports `"Direct3D 11 (feature level 10.1 floor)"`. No action. |

## 3. What DirectExp already provides (verified in source)

The DirectExp docs say several of these are missing. The code says otherwise.

| Capability Sodium needs | Where | Status |
|---|---|---|
| `multiDrawDirectInterleaved = true`, limit 65536 | `DxDeviceBackend.FEATURES` / `DEFAULT_LIMITS` (record order checked against `DeviceFeatures`: `wireframeFillMode`=true, `multiDrawDirectInterleaved`=true, `persistentMapping`=false) | Done. Pinned by `DxDeviceBackendFeaturesTest`. |
| `persistentMapping = false` | same | Done. Sodium then uses `writeToBuffer` and never reaches `MappedStagingBuffer` (which casts to `GlBuffer`/`GlDevice`). |
| `RenderPass.pushConstants(ByteBuffer)` | `DxRenderPassBackend.pushConstants` -> `DxPushConstantStore`, exposed to the shader as cbuffer `DxPushConstants` | Done. Copies the bytes, so Sodium's stack-allocated buffer is safe. |
| `multiDrawIndexed(IntBuffer, 1, 0, n)` reading `[firstIndex, indexCount, baseVertex]` triples, one native call per batch | `DxRenderPassBackend.multiDrawIndexed` -> `dxBridge.multiDrawIndexed` | Done. Accepts direct native-order buffers without copying. Push constants are staged once per call, so the old "restage per sub-draw" hazard is gone. |
| Separate-array `multiDrawIndexed(PointerBuffer, ...)` | same class | **Throws.** Not needed for the recommended design. |
| Texel buffer for `u_SectionTimeInfo` | `DxBufferBinding.USAGE_UNIFORM_TEXEL_BUFFER`, `bufferShaderResourceHandle`, texel-buffer binding in `DxResourceBinder` | Present. Old plan listed it as a leftover. Needs a runtime check (fade-in). |
| Buffer `map(false, true)` for write, including large GPU-only index/vertex buffers | `DxBuffer.map` / `mapGpuOnly` (temp CPU buffer uploaded on close) | Present. Used by Sodium's shared index buffer and section-time buffer. |
| `copyToBuffer`, `writeToBuffer` | `DxCommandEncoderBackend` | Present. |
| Sodium vertex format `RG32_UINT`, `RGBA8_UNORM`, `RG16_UINT`, `RGBA8_UINT` | `DxPipelineStateMapping.vertexAttributeFormat` | Mapped (`0x11`, `0x1c`, `0x24`, `0x1e`). |
| `QUADS` topology + 32-bit index buffer | `topology()` maps to TRIANGLELIST; Sodium supplies 6 indices/quad | Fine. |
| Multi-slot vertex buffers, up to 8 color targets | `DxPipelineStateMapping.describe` | Implemented. **The gap-plan doc says these are rejected and `maxColorAttachments` stays 1; the code sets 8.** Doc is stale. Sodium itself only uses slot 0. |

## 4. Design

### Option A (recommended): Direcium reduced to one mixin

Make Sodium treat DirectExp as `VK_MULTIDRAW`. Sodium's stock Vulkan classes then do the right thing with no new draw code:

- `VKMultiDrawBatch` writes LWJGL `VkMultiDrawIndexedInfoEXT` records (`firstIndex`, `indexCount`, `vertexOffset`; 12 bytes). That is the same triple order DirectExp reads. `elementOffset` is stored unshifted, i.e. in index units, which is what DirectExp wants.
- `VKMultiDrawContext` only stores the pass. Per-region constants already go through `pass.pushConstants`.
- `draw` calls `multiDrawIndexed(memIntBuffer(..., size * 3), 1, 0, size)`, exactly DirectExp's fast path.

```java
@Mixin(DrawBackend.class)
public abstract class DrawBackendMixin {
    @Inject(method = "chooseBackend", at = @At("HEAD"), cancellable = true)
    private static void direcium$chooseForDirectExp(CallbackInfoReturnable<DrawBackend> cir) {
        if (DirectExpBackend.isActive()) {
            cir.setReturnValue(DrawBackend.VK_MULTIDRAW);
        }
    }
}
```

`chooseBackend()` runs from the enum's static initializer, after the constants exist, so returning `VK_MULTIDRAW` there is safe. Keep `defaultRequire: 1` so a Sodium rename fails loudly.

**Side benefits:** Direcium no longer needs DirectExp's `DxPushConstants` at compile time, so the only coupling to DirectExp is the backend-name string. The F3 line shows `Terrain Rendering: ext_multidraw (sodium)`, which is a useful smoke signal.

### Option B (alternative, can retire Direcium for terrain)

Implement `multiDrawIndexed(PointerBuffer firstIndexOffsets, IntBuffer indexCounts, IntBuffer vertexOffsets, int drawCount)` in `DxRenderPassBackend`: convert each byte offset to an index (`offset >> log2(indexSize)` from the bound `IndexType`), interleave into the existing `[firstIndex, indexCount, baseVertex]` buffer and reuse the current native batch path. Sodium then picks `OPENGL` and `GLDrawBatch` works unmodified.

| | A (mixin) | B (DirectExp overload) |
|---|---|---|
| New code | ~30 lines in Direcium | ~40 lines + tests in DirectExp |
| Depends on Sodium internals | `DrawBackend.chooseBackend` name | Only public Mojang API |
| Needs LWJGL Vulkan classes at runtime | **Yes** (`VkMultiDrawIndexedInfoEXT`) | No |
| Needs Direcium | Yes | No (except the settings UI, section 6) |

Recommendation: do A first. It needs no DirectExp change and reuses the already-implemented fast path. If the LWJGL Vulkan check in phase 2 fails, or Sodium keeps renaming internals, do B. They do not conflict.

## 6. Settings UI gap (Sodium replaces the video screen)

- DirectExp adds its Graphics API option by redirecting `VideoSettingsScreen.addOptions` and the restart-warning checks (`VideoSettingsDisplayOptionsMixin`, `VideoSettingsRestartWarningMixin`).
- Sodium's `OptionsScreenMixin` replaces the Video Settings button with Sodium's own screen. The DirectExp mixins still apply, but nobody opens that screen. A user on DirectX with Sodium installed has **no way in the UI to change the API back**. The saved choice still applies at startup.
- Fix in Direcium: implement `ConfigEntryPoint.registerConfigLate(ConfigBuilder)` and register an enum option for `BackendKind` on a "DirectExp" page. Read and write it the same way `DirectExpGraphicsApiOptionFactory` does, and report "restart required" via `DirectExpGraphicsApiSelectionState` / Sodium's option state.
- I did not read `DirectExpGraphicsApiOptionFactory` in detail, so the exact getter/setter wiring is a to-do. `ConfigBuilder`, `EnumOptionBuilder` and `OptionPageBuilder` exist in Sodium's `api/config/structure`.
- Optional alternative: make DirectExp expose this itself so Direcium only calls it.

## 7. Risks and unknowns (need a Windows run)

| # | Risk | Why it matters | Check |
|---|---|---|---|
| R1 | **LWJGL Vulkan classes on the classpath** (Option A) | `VKMultiDrawBatch` loads `org.lwjgl.vulkan.VkMultiDrawIndexedInfoEXT`. Its layout is pure Java and should not need a Vulkan driver, but the jar must be present. | Launch; look for `NoClassDefFoundError`. Fallback: Option B. |
| R2 | **Sodium's shaders through Shaderc -> SPIR-V -> SPIRV-Cross HLSL** | Needs `isamplerBuffer` + `texelFetch`, `textureGrad`, `dFdx/dFdy`, integer vertex inputs (`uvec2`, `uvec4`), a `bool` in the std140 `u_Globals` block, a push-constant block, `#moj_import`-style includes (`sodium:globals.glsl`, `minecraft:oit.glsl`). None were run through DirectExp's native path in the material I read. | First pipeline compile; watch for "HLSL emission/compilation failed" and invalid-pipeline logs. |
| R3 | **`u_SectionTimeInfo` as `Buffer<int4>` SRV** | Wrong binding shows as no chunk fade-in or an unbound-texture log. | Move through terrain; confirm fade. |
| R4 | **Arena buffer size vs. D3D11 limits** | Sodium allocates large per-region vertex arenas (`ArenaAggregator`). D3D11 caps single resource size by feature level and VRAM. I did not determine Sodium's maximum arena size. | Render-distance sweep; look for buffer-create failures. |
| R5 | **OIT** | Sodium builds `OitPipelineSet` pipelines when Minecraft passes a non-null `OitStage`. DirectExp now advertises `maxColorAttachments = 8`, so the game may choose OIT. DirectExp's own plan says OIT was meant to stay off. Whether the multi-target path renders correctly is unverified. | Test with the transparency/OIT option on and off; if broken, lower `maxColorAttachments` in DirectExp or document it. |
| R6 | **Device is non-null when `DrawBackend` initialises** | `chooseBackend` runs once. If our check runs while the device is null, `isActive()` returns false and the choice sticks. Stock Sodium would NPE in that case anyway. | Confirm the F3 line says `ext_multidraw`. |
| R7 | **Frontend validation of `multiDrawIndexed`** | The frontend `RenderPass` implementation wasn't in the files I read (only the interface). It may check the feature flag and the draw-count limit (max batch is `7 * 256 + 1 = 1793`, limit is 65536). | Covered by any terrain frame. |
| R8 | **Sodium update drift** | Surface is one private method name and the enum constant name. | `defaultRequire: 1` + the startup check in 5.3. |
| R9 | **Performance** | Region draws are one native call each, but arenas, per-frame constant staging and the CPU-mirror policy still cost. | Compare with vanilla DirectExp; profile with `DxPerformanceProfiler`. |

## 8. Phases

**Phase 1: Bring Direcium to 26.3 (no behaviour yet).**
Update `gradle.properties`, `fabric.mod.json`, `libs/`. Delete the files in 5.1. Fix `DirectExpBackend`. Keep `DirectExpBackendNameTest` green.
*Exit:* `./gradlew build` and `test` pass against the Sodium 26.3 jar.

**Phase 2: Terrain path.**
Add `DrawBackendMixin`, update the mixin JSON and `DireciumClient`. Launch with DirectExp + Sodium at a small render distance.
*Exit:* F3 shows `ext_multidraw (sodium)`; terrain (opaque, cutout, translucent) draws; no GL calls; no invalid-pipeline entries for `sodium:*`.
*If R1 fails:* implement Option B in DirectExp.

**Phase 3: Correctness matrix** (rewrite `docs/test/phase-d-correctness-matrix.md` for 26.3).
Resize, fullscreen, F3+T reload, dimension change, long session, render-distance sweep (R4), fog / RGSS / anisotropy, translucency sorting modes, chunk fade-in (R3), OIT on/off (R5), Sodium vs. vanilla DirectExp comparison.

**Phase 4: Settings UI.**
Implement the `sodium:config_api_user` entry point (section 6) and test switching the API with Sodium's screen.

**Phase 5: Performance** (in DirectExp, only after Phase 3): GPU-only arena buffers, native buffer copy, remaining per-frame staging.

**DirectExp housekeeping (any time):** update `docs/plans/2026-10-24-directexp-required-pipeline-gaps-plan.md` and the 26.3 migration note to match the code (multi-slot and multi-target are implemented, D1 is done, `maxColorAttachments = 8`), and update the README's Sodium line to point at this flow.
